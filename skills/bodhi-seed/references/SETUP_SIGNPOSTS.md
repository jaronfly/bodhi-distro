# Early signposts — save future time without building everything today

After the first useful result, mention at most one or two of these when Player One's stated plans make them plausible. Frame each as “If you expect to…, consider…” and let them defer it. Show the smallest existing option before naming a larger system. Do not infer a whole career or lifestyle from one request.

| If Player One expects to… | Foreshadow this | First small step |
|---|---|---|
| Revise many creative or development projects | Version control makes changes, attribution, and rollback visible. | One Git repository per active project, with a short README; a private remote or backup when appropriate. |
| Use several models, providers, or token pools | Keep a record of which model handled which task and what quality/cost it delivered. A router or fleet manager becomes useful when handoffs or fallbacks get messy. | Try the chosen harness's provider and fallback controls before adding Herdr-like coordination. |
| Use more than one harness or machine | A shared handoff surface prevents “I told the other agent” from becoming an invisible assumption. | Name the task, source, owner, and acceptance test in a channel the agents can actually access; read back the result. Buzz, Discord, or a message board are options, not prerequisites. |
| Let jobs run unattended | A dashboard or status view should show last run, failures, and actual output, not only an “online” light. | Inspect the harness's built-in job history and alerts before building another dashboard. |
| Repeat a workflow that worked | A short user-owned skill can spare another session from rediscovering the procedure. | Ask the harness to learn or draft the routine from the actual run; in Hermes, `/learn` is one supported path. Test the new skill on a fresh example before relying on it. |
| Work with external apps or accounts | A connector or MCP tool may save repeated copy/paste. | Pick one task and confirm the tool, permissions, and destination result. |
| Collect browsing, screen, audio, or other personal data | Capture can help surface missed interests, but scope and source identity matter. | Choose one surface and test an opt-in capture path using tools the harness already supports. |
| Deploy an always-on service | Containers or Kubernetes can help with isolation and recovery at a scale that needs them. | First confirm the service's uptime and deployment problem; a single post or research task does not need infrastructure. |

For continuity, ask where Player One wants durable context to live: the harness's memory, an existing workspace or project repository, or an optional source vault. Use that chosen path for a short record of their own words about the priority, the first result, corrections, and the next useful action. Show inferred profile details for correction before treating them as facts. In a fresh session, check whether that context was retrieved accurately. If it was, adapt the local instructions or skill to the person, then retire the generic seed. If it was not, fix the chosen harness path before inventing a second memory engine.
