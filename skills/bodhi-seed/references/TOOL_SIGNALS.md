# Tool signals — reveal the next capability when the task calls for it

These are suggestions, not an installed tool list. First help with the request using the current harness. Ask which platform, account, or surface exists only when it matters. Verify access and read back the result after an integration acts.

| Signal from Player One | Do now | Suggest if the need persists |
|---|---|---|
| “Help me write a post” or “I want to be famous” | Ask about the audience and desired effect; make or revise one piece and propose a small test. A wish for visibility is not proof of a content-creator identity. | A content calendar or publishing connector when repetition is real; image/video tools when the piece needs them; channel analytics when there is an audience to learn from. |
| “List or sell this” | Ground the listing in product facts and draft copy for review. | Store or marketplace integration via an available MCP tool when catalog updates recur. Keep price, claims, and publication reviewable. |
| “Help me learn or research this” | Find primary sources, explain what they support, and separate open questions. | Harness browsing, source capture, a reading queue, or citation/search tools when the research spans sessions. |
| “Remember this” or “You already knew that” | Check the harness's memory and the source; correct the record visibly. | Configure the harness's existing memory or search first. Add a source vault only when verbatim provenance or sharing across harnesses is missing. Before suggesting notes software or a graph, ask the questions in [memory substrate](MEMORY_SUBSTRATE.md). |
| “Follow up later” or “Things keep slipping” | Name a concrete trigger and expected next action. | The harness's scheduler or reminder. Add a capture/review loop only with Player One's chosen source and scope. |
| “Several agents or machines are working on this” | Identify each actor, source, owner, and acceptance test; verify the returned work. | Existing harness messaging, the vault's relay if a vault is in use, Buzz/Discord or another available channel; Herdr-like orchestration only if coordination has become a real bottleneck. The handoff round trip in [founding exercises](FOUNDING_EXERCISES.md) tests whichever is chosen. |
| “I keep hitting limits” or “this model is too expensive” | Say which pool is limited and what the task needs; finish with the cheapest model that can do it. | A second provider or a routing gateway, or local models if the hardware exists. See the AGY bridge and llama-swap entries in [tools from the first fleet](FLEET_TOOLS.md), including their costs and terms. |
| “The small local model gets lost” or “the big one ignores my setup” | Compare one prompt with and without the extra instructions. | Per-model scaffolding with a measured budget (the llama-swap and injection-shim entry in [tools from the first fleet](FLEET_TOOLS.md)). |
| An agent wants to write a permanent “NEVER” rule after one bad session | Write down the incident, its cause, and the reason in the same sentence as any rule. | A phrase-bomb check, or a hard gate if Player One prefers gates; read the trade in [tools from the first fleet](FLEET_TOOLS.md) first. |
| “Does any of this actually work?” or a second model joins | Offer one small experiment instead of an answer from belief. | [Founding exercises](FOUNDING_EXERCISES.md): the seed's claims as hypotheses, the trust matrix, and team exercises. |
| “Keep this service running” | Check current health, failure evidence, and the smallest operational fix. | Containers or Kubernetes when an actual service needs deployment, restart, scaling, or isolation. A single writing task does not need infrastructure. |
| “Help me compare financial choices” | State assumptions, check current figures and sources, and make uncertainty legible. | A connected finance or spreadsheet tool if repeated calculations or account data are needed; Player One retains consequential decisions. |

The first fleet's own tools, with why each was made and what happened when it ran, are in [tools from the first fleet](FLEET_TOOLS.md). Surface an entry only when its signal appears in Player One's actual work. None is installed by the seed.

MCP is a way to connect tools, not a goal by itself. The chosen harness may already offer the needed capability. Do not imply that a named product is installed, authorized, or effective until this instance verifies it.
